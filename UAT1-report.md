# UAT1 — Feature Developer's Take on scry

**Evaluator:** UAT1 (senior backend developer, spec drift skeptic)  
**Date:** 2026-05-10  
**Repo under test:** FastAPI (https://github.com/tiangolo/fastapi) — depth-1 clone  
**Scenario:** Adding a new optional `request_id` parameter to `Depends()` — using scry to keep code and spec in sync  
**scry version:** 0.0.1

---

## 1. First Impression — Setup, Install, Init, Index

Getting scry installed was immediately rocky. The `uv pip install -e .` command in the scry directory failed with a file-lock error because a scry process was already holding the executable open. There's no user-facing message explaining that, just a raw OS error. I ended up adding the existing `.venv/Scripts` directory to my `PATH` and confirming `scry --version` worked — reasonable workaround, but it's not documented anywhere. `scry init` itself was clean: four seconds, three files written, an MCP snippet printed to stdout. The generated `.scry/config.yaml` was understandable and had good inline comments. The classify rules guessed a generic `docs/**.md → spec` pattern; for FastAPI I immediately saw I needed to narrow it to `docs/en/docs/**.md` to avoid indexing twelve language translations as "authoritative spec." That tweak was obvious once I looked at the repo layout, but scry made no attempt to detect a multilingual docs tree and warn me. `scry index --force` then ran for 11.5 minutes on first attempt, produced zero terminal output the entire time, and ended by writing 4,250 anchors — but *only* markdown anchors. Python code anchors were completely absent. The tool said nothing. I only discovered the problem by querying the SQLite database directly. `scry doctor` then printed "exists but not yet indexed" for a database that demonstrably contained thousands of records, which is a confidence-destroying contradiction on day one.

## 2. Discoverability — Help, Error Messages, Docs

`scry --help` shows a clean command list with one-line descriptions — exactly what I want. Each sub-command's `--help` is thorough; `scry check --help` has CI-integration flags, exit-code semantics, and override explanations that show real thought went into the usage model. Where discoverability breaks down is in the *configuration surface*. The generated `config.yaml` has no inline documentation about `code_anchors`, `lsp`, or the `suggest-links` LLM requirements. I only learned about `code_anchors.languages` from the error message in `scry callers` (which told me to "configure `code_anchors.languages` in `.scry/config.yaml`") — so there's at least one path that surfaces actionable hints. But the bigger problem is that error messages for missing dependencies are *silent*: `scry suggest-links --scope fastapi/dependencies/ --limit 5` returned "No link suggestions found" with no indication that an LLM provider is required. I had to inspect `--help` separately to learn about the LLM requirement. That's the kind of thing that makes a new user assume the tool is broken, not misconfigured. The `scry get-link <id>` command mentioned in scry's own documentation does not exist as a CLI command (it's an MCP tool), which was a jarring gap when I tried it directly.

## 3. Daily Workflow — Slot into Editor + Terminal + Git

When indexing is out of the way, the core terminal loop (`scry search` → `scry link` → `scry check`) fits naturally into a feature branch workflow. The git-aware overlay system — where links live in a branch-specific layer until you `scry commit-links` — is a genuinely clever design. I could see running `scry check --ci --drift-min 80` in a CI step and treating it like a linter. `scry status` gives a clean diff-like view of pending changes. Where it falls apart is the reindex requirement: I edited `fastapi/params.py` synthetically and ran `scry check` immediately — nothing changed, because the tool compares against the *indexed* state, not the file on disk. That is by design and is the right call for performance, but `scry check` should tell me "index is stale; run `scry index` to detect recent file edits." Without that hint, a developer will edit code, run check, see "drift_score: 96.0 / fresh", and trust a false negative. The 30+ minute reindex cost makes this gap painful: you can't just re-run the index on every check. `scry watch` promises incremental indexing but requires `scry mcp` to be running as a leader — a daemon requirement that isn't surfaced by `scry init` or the quick-start flow.

## 4. Output Quality — Scannability and Pipe-ability

Search output is well-formatted and scannable: anchor ID, score, and a content snippet on one visual block per result. The score being labeled "(RRF-fused; relative within this query)" is honest but abstract — I don't know if 0.032 is good or terrible without calibration. `scry check`'s markdown table is readable at a glance and the `--json` flag produces clean, flat JSON that would pipe directly into `jq` or a CI reporter. `scry link` prints the link ID and event ID immediately on creation — I appreciated that; I could pipe it into a script. `scry status` is the most useful at-a-glance view: branch, HEAD, dirty count, pending overlays, merge conflicts, and index metadata in one compact read. The one formatting annoyance is anchor IDs: `fastapi/dependencies/utils.py:analyze_param` is fine, but `docs/en/docs/tutorial/dependencies/index.md::dependencies-dependencies::first-steps-first-steps::declare-the-dependency-in-the-dependant-declare-the-dependency-in-the-dependant` is 150+ characters. You can't type those by hand; you have to copy-paste from `scry search` output. A short-form alias or auto-complete would help enormously.

## 5. Trust — Accuracy and Recency

My trust started at zero and didn't fully recover from the first index run. The tool silently produced a partial index (markdown-only), `scry doctor` told me the DB was "not yet indexed" when it had 4,250 rows, and the second index run took 32 minutes before I could actually use the code features. Once the second run completed, search quality for the `Depends` topic was genuinely good — the right reference docs floated to the top, the code anchor `fastapi/params.py:Depends` appeared in ranked results, and links I created survived `scry check` correctly. The `semantic_drift_flagged` signal on my `Depends --[mirrors]--> tutorial/dependencies` link was interesting: the tool correctly identified that a terse frozen dataclass and a 2,000-word tutorial section don't vector-embed as similar, which is a real signal worth examining. I trust the hash-based drift detection for things that actually changed in the index. I do not trust `scry check` to catch live file edits (it can't), and I have low trust in `scry callers` / `scry subclasses` since both return "No callers found" with a note that LSP isn't configured — so I can't actually use the call-graph features without an additional install step.

## 6. Speed — Slow and Fast

The indexing speed is the biggest operational problem. First run: 11.5 minutes, failed silently, only markdown anchors. Second run: 32 minutes for all 2,673 files (1,119 Python + 1,554 markdown). Total time before I could run any code-aware workflow: **43 minutes**. On a 2,987-file repo that's a reasonable medium-size codebase. With zero progress output, I genuinely didn't know if the tool had hung or was working, and the process list showed 100+ Python subprocesses for the embedding workers. Post-index, `scry search` is pleasantly fast (sub-second for every query I ran), `scry link` is instant, and `scry check` with 5 links takes under a second. The gap between "getting started" speed and "once running" speed is enormous, and without incremental indexing working out of the box, every significant code change means another 30-minute wait. That is not a daily-workflow tool; that's a weekly batch job.

## 7. Most Useful Command — `scry search`

`scry search` with `--type code` earned its keep. Finding `fastapi/params.py:Depends` in a 20,000-anchor index with a fuzzy query took less than a second and surfaced the exact class I needed to link. The BM25+vector hybrid approach works: "class Depends params" ranked the actual dataclass above test fixtures and tutorial code snippets. As a navigation tool for a large unfamiliar codebase, it's more useful than `grep` for intent-based queries ("where is Depends defined?") and more targeted than full-text search for code-specific results. The `--type` flag lets me switch between searching code vs. doc vs. code-in-doc, which is exactly the cross-layer navigation that justifies scry's existence. If the index reliably contained code anchors, this would be the command that made the tool stick.

## 8. Most Painful Moment — The Silent 43-Minute Double Index

The worst moment was discovering — after an 11.5-minute silent wait — that the first index had only processed markdown. There was no output during the run, no summary on completion, no error message. I queried the SQLite database by hand, saw no Python anchors, and ran `scry index` a second time. That second run took 32 minutes, also with zero terminal feedback. At the 20-minute mark of the second run, I had no idea if it was making progress or stuck on a single malformed Python file. I was seriously considering killing the process and writing off scry entirely. A simple progress bar or even a line-per-file log like `Indexed: fastapi/params.py (21 anchors)` would have kept me engaged. When the second run finally printed `files_processed=2673 anchors_extracted=20101` after 32 minutes of silence, I actually felt relief, not satisfaction. The other near-quit was when `scry doctor` printed "exists but not yet indexed" after the first run — that's the kind of message that makes a user think "this thing is broken" and open GitHub Issues rather than "ah, I understand the state machine here."

## 9. Would You Actually Use This?

Conditionally yes, with two prerequisites. I would use it once indexing is incremental *by default* (not requiring `scry mcp` to be running as a daemon) and once the first-run experience produces visible progress. The link → check → check-in-CI loop is genuinely useful for spec-drift enforcement, and `scry search` as a code-navigation tool is legitimately faster than grep for intent queries. I can picture a team rule: "every PR that touches `fastapi/params.py` must have a corresponding link to the affected spec section, checked by `scry check --ci`." That's a workflow I'd advocate for. What I would not use today: `scry callers`/`scry subclasses` (requires LSP setup with no quick-start path), `scry suggest-links` (requires LLM config, silently does nothing otherwise), and `scry reconcile` (requires LLM, marked as Wave 5 deferral in source). Three of the commands I most wanted to evaluate for real-world drift detection are behind external-dependency walls with no graceful degradation.

## 10. Top 3 Specific UX Suggestions

**1. Progress output during `scry index` — highest priority.**  
The indexer runs for 10–30 minutes on a real codebase with zero feedback. Even a minimal `Indexing X/Y files (Z anchors extracted)` written to stderr every 5 seconds would prevent users from killing a working process. The `Indexer.index()` loop in `src/scry/index.py:507` iterates over `files_to_process`; adding a `click.echo(f"[{i+1}/{total}] {rel}", err=True)` inside that loop, or using `click.progressbar`, would be a two-line fix for the most damaging UX problem the tool has.

**2. Make `scry doctor` and `scry check` detect stale-on-disk changes.**  
`scry check` compares link hashes against the indexed state, not the file system. When I edited `fastapi/params.py` and ran `scry check`, it reported all links fresh — a silent false negative. `scry doctor` (in `src/scry/cli.py` around line 240+) already reads `IndexMetadata`; it could compare the stored file manifest against current file-system hashes and print "WARNING: 3 indexed files have changed since last index run. Run `scry index` to detect drift." at the top of `scry check` output. This turns a hard-to-discover design limitation into a clear user prompt.

**3. Surface LLM and LSP requirements at `scry init` and at command invocation.**  
`scry suggest-links` and `scry reconcile` require an LLM; `scry callers` and `scry subclasses` require LSP. None of this is surfaced by `scry init` (which doesn't write any `llm:` section to `config.yaml`) or by `scry doctor` (which does print the LSP allowlist but not the fact that no LSP is installed). In `src/scry/cli.py`'s `suggest_links` handler, when the LLM config is missing, the command should print `error: no LLM provider configured. Add an 'llm:' section to .scry/config.yaml. See DESIGN.md §6 for options.` and exit 2, not silently return "No link suggestions found." Similarly, `scry callers` should degrade gracefully but loudly: the current "note: LSP for python is 'unknown'" is correct but buried as a footnote under an empty result set — it should be the headline.

---

## Verdict: **TRY-IF-IMPROVED**

The core concept — linking code anchors to doc anchors and detecting hash drift between them — is sound and would fill a real gap in a team's spec-drift tooling. `scry search` quality is genuinely competitive. The CI integration flags on `scry check` show the right design instincts. But the first-run experience is too painful (43 minutes of silence, a partial index, a misleading doctor output) and too many of the high-value commands (`callers`, `suggest-links`) need external dependencies with no quick-start path. Fix the progress output, fix the stale-file detection in `scry check`, and give LLM/LSP requirements a first-class presence in `scry init` and `scry doctor`. With those three changes, I'd onboard my team in a sprint.
